Lifelong learning has always been a big motto of mine. It’s just a bit tragic that there’s so much to learn and so little time.

Lately, I’ve been struggling to find direction in my career. There’s a lot of exciting stuff happening in tech, and the question that keeps coming up is: where do I even start?

I’ve realized that this question itself has been a bit of a blocker. It assumes there’s a clean, organized, straightforward path — when in reality, that’s rarely how things work. That’s where this internal tug-of-war started: between a structured, sequential learning path and a more Just-In-Time (JIT) approach. Deep down, I’ve always known I learn best by doing — by building, experimenting, and figuring things out as I go. But at the same time, I couldn’t shake the feeling that the “right” way to learn was the structured one.

A lot of that came from how we’re taught to think about expertise. Academics — the people doing cutting-edge work often follow a very sequential path: formal education, strong theoretical foundations, then years spent going deep into a specific area. And it’s hard not to look at that and think, that must be the right way to do it.

So even though hands-on learning felt more natural to me, I kept gravitating toward the structured path of building foundations, covering breadth, and delaying depth because it felt more legitimate.

But from what I've realised, sequential learning really doesn't play to my strengths because for all my life, I've been a hands on person. And as someone who learns best by doing, that kind of sequential learning just doesn’t click. It’s hard to connect it to anything practical, and with so many books and resources pulling you in, you end up with this comforting sense of progress. The danger here is that they are all well structured enough to feel like progress while you're going through them. Each chapter builds on the last, the code runs, you feel productive. But at the end you've reproduced someone else's understanding in a controlled environment with no friction, which means very little of it will stick and none of it will surprise you. That's tutorial hell by a more respectable name.
As an example, I remember in my early 20s when I was trying to learn web dev. I had attended this hackathon and the organisers had proposed we use React (though it wasn't a hard rule). Until that point in my life, I had never heard of React and felt severely inadequate for not knowing it among my peers.

So I remember going back home and pulling up tutes on React and web dev. I built countless todo apps and components, constantly Googling stuff, like the what was the difference between state and props, what is a spread operator and so on until I got to this point where I could build components and web pages effortlessly. And to be fair, I did try to follow some tutorials sequentially, but I felt I was better off doing something of my own volition. I believe I got good because I didn't wait to read the docs from start to finish, or understand every single hook, or why function-based components (which was new back then) was better than class based components, or why memoisation was important etc.

Compare that to my recent dabbling in Reinforcement Learning (RL). It’s a fascinating area, but also incredibly complex. Since I’d never really dealt with something at that level of complexity before, my imposter syndrome kicked in pretty quickly. I convinced myself that to really understand RL, I needed to understand everything — the theory behind it, the optimization machinery, probability, MDPs, all of it. So I went all in: working through derivations, reading papers, watching lecture series from start to finish… or at least trying to. In reality, I never actually made it all the way through any of them. And while I did write the code for RL agents from scratch, using (Gymnasium)[https://gymnasium.farama.org/] as the playground, the reality was that I never really learnt all that much. As I mentioned, the RL space is enormous, and hoping to gork RL within a few months was quite naive.
In hindsight, I imagine a better plan would have been to use an existing RL library, pick an algorithm and run it against a game, or even perhaps create a multi-agent environment and compare how agents fare against each other.

The JIT approach has a compounding property that sequential learning lacks - anything you learn is load bearing, which means it stays with you longer. Sequential learning on the other hand has a high decay rate. The way to use sequential resources is as a reference around some kind of work or idea that you were curious about.

I'm not saying sequential learning is useless. I think its extremely important in an academic context. The goal of sequential, exhaustive learning is to produce someone who can situate their work within a complete literature, pass qualification exams, and write papers that reviewers can't fault for missing prior art. That's a legitimate goal for a specific career path. And like most things, the truth is somewhere in the middle. A field where JIT tends to be weak is probably mathematics. 

There is however one genuine caveat with JIT learning - you tend to have blind spots around things you don't know you don't know. You only pull in knowledge when a problem surfaces the need, which means if a problem never surfaces a particular gap, the gap stays. The mitigation is staying in conversation with others doing similar work — not to learn sequentially from them, but to occasionally have someone point at something you walked past.
